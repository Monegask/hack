## Быстрый локальный запуск на этом Windows

1. Открыть `Start-PvP.cmd` (зависимости и сборка уже подготовлены в рабочем проекте).
2. Открыть **http://localhost:4190/pvp/** в двух отдельных профилях браузера.
3. Подключить два разных Testnet-кошелька. Каждому нужны test NEAR на gas и тестовые FT для ставок.
4. Первый создаёт лобби, второй открывает приглашение. Оба проверяют сумму и вносят депозит. Матч стартует после подтверждения двух депозитов. По окончании приз и комиссия сверяются с final on-chain состоянием.

`localhost` доступен только на этом компьютере. Для двух разных компьютеров нужен публичный HTTPS backend; пользователь сообщил, что VPS пока нет. На опубликованном Vercel сейчас остаётся прежний сайт, а не эта локальная сборка.

С нуля: `npm ci`, затем `npm run build` в этой папке; для пересборки игровых артефактов сначала выполнить штатные `../build-offline.cjs` и `../bot/build-race.cjs`. Не очищать localStorage одиночной игры. Сборка использует `../logistics-race-bot.html` и заменяет бот-адаптер на авторитетный сетевой клиент.

## Что реализовано

- Подключение Testnet-кошелька через NEAR Connect 0.12.0, серверная аутентификация NEP-413 с одноразовым challenge и проверкой Full Access публичного ключа в Testnet. Приватный ключ игрока остаётся в его кошельке.
- Приглашение по ссылке/коду, два фиксированных участника, равная ставка 1–100 тестовых токенов, комиссия из конфигурации существующего escrow (сейчас 3% банка).
- Настоящая текущая экономика 12/6/8, зеркальная seeded-карта, две независимые экономики с общей дорогой, серверные часы 1×. Команды валидируются и выполняются только на сервере. Клиентские `won`, localStorage, ресурсы и часы не определяют результат.
- Точные `ft_transfer_call` с match/revision/stake/fee, отдельная регистрация FT, старт по final ReadyToStart и on-chain countdown. Приз и комиссия определяются контрактом; UI различает Ready/InFlight/Paid. Claim не повторяет InFlight.
- Отмена до старта, сдача, согласованная отмена, emergency refund; независимый worker heartbeat. При одиночном disconnect >120 секунд сервер подаёт результат в пользу подключённого соперника. При двойном disconnect/одновременном финише игра останавливается, heartbeat этого матча прекращается: два участника могут сразу согласовать возврат, либо каждый получает право на emergency refund через 1800 секунд от последнего on-chain heartbeat. Это ограничения текущего escrow, а не мгновенный автоматический возврат.
- SQLite WAL с полными снимками и журналом идемпотентных команд. Подписанные серверные транзакции сохраняются ДО отправки; при неизвестном ответе повторяется та же подписанная транзакция, без новой подписи. Сбой, не позволяющий установить final outcome, требует сверки receipt/операции, а не очистки БД.
- Восстановление после перезапуска ждёт подключения обоих участников. Время простоя не симулируется заново. Протухший heartbeat не возобновляется.
- Перед запуском: проверка сети, escrow code hash против сохранённого WASM, token/server/decimals, регистрации escrow и ограничений runtime key. БД имеет lease против двух активных процессов. Старт после аварии может ждать истечения lease до 15 секунд.

Параметры Testnet 1–100, 120 секунд, 3% и правила спорных исходов — конфигурация/правила этой пробной поставки. Это не утверждение денежных правил Mainnet. Intents, Mainnet, публичный matchmaking, Raise negotiation, независимый dispute protocol и аудит безопасности в поставку не входят.

## Подготовленное размещение на VPS

Пакет `output/releases/supply-line-testnet-pvp/` содержит только runtime, встроенную игру, lockfile, проверочный WASM и Docker/Caddy-конфигурацию. Это отдельный HTTPS-сайт для PvP; переносить текущий Vercel для первого теста не требуется.

На Linux VPS с Docker Compose, доменом с A-записью и открытыми 80/443:

1. Распаковать пакет; скопировать корневой `.env.example` в `.env`, указать домен, два Testnet account ID и абсолютный путь к runtime key **вне** распакованного проекта.
2. Передать только ограниченный server-runtime через защищённый канал. Файл должен читаться UID 1000 контейнера; например владелец `1000:1000` и права `0400`. Не передавать admin/deployment/player ключи серверу.
3. В корне пакета выполнить `docker compose up -d --build`, затем `docker compose logs pvp`. После успешного preflight открыть `https://ВАШ-ДОМЕН/pvp/`.

Контейнер работает без root, с read-only filesystem; `/data` хранится в постоянном томе, ключ монтируется read-only как secret. **Docker deployment на настоящем VPS пока не выполнялся**, доступного сервера нет. Процесс рассчитан на один экземпляр; не масштабировать его через `--scale`. 2 vCPU/4 GB — начальная оценка до нагрузочной проверки, не обещанная вместимость.

## Проверки и эксплуатация

`npm test` — backend/auth/outbox/recovery и полная партия с автоматическими игроками на настоящем движке. Блокчейн в этих тестах имитируется, финансовые receipts проверяются отдельными Rust/Sandbox тестами escrow. `node tests/browser-qa.mjs` — два изолированных headless Edge-клиента, реальные HTTP-команды, зеркальные стороны, reload, восстановление после подмены клиента, мобильное лобби; используются тестовые сессии только внутри QA-скрипта, production login bypass отсутствует.

`npm run preflight` с настроенным `SERVER_KEY_FILE` — read-only проверка сети и signer. `npm start` — настоящий Testnet backend. Запуск сам по себе не создаёт матчей и не вносит ставки.

Online backup: `node server/backup.mjs /absolute/external/path/pvp-backup.sqlite`. Проверка backup/restore входит в тесты. Хранить копию вне VPS. При восстановлении старой резервной копии **не запускать сервер автоматически**: новые матчи/депозиты могли появиться после копии. Сначала сверить все on-chain active matches и outbox; потерянная запись активной игры означает остановку heartbeat и разрешённый возврат, а не новую партию с нуля. Штатный restart использует текущую WAL-БД и не требует восстановления backup.

Нужно наблюдать: last successful heartbeat каждого матча, ошибки RPC/подписанных операций, Ready/InFlight payouts, запас native NEAR сервера/escrow, FT-регистрации, размер БД и backup. Нет автоматического безопасного сброса неизвестной выплаты/транзакции. Сервер доверенный: он определяет победителя; серверный доступ и deployment governance требуют отдельной проверки перед Mainnet.

Свежая проверка настоящих выплат через эту игровую связку пока ожидает два кошелька и доступ владельца тестового FT. Старый завершённый on-chain матч №0 существует отдельно и не выдаётся за прогон новой интеграции.

Список кошельков проверен на настоящем локальном backend: для Testnet и подписи сообщения доступны Meteor/Intear и другие совместимые варианты. MyNearWallet в текущем фильтре этих возможностей не показывается. Выбирать кошелёк из окна Connect Testnet wallet; для двух игроков нужны два отдельных профиля/аккаунта.
