# Supply Line — производительность PvP, 13 ноября 2026

Ветка `perf/pvp-scalability`, отдельный worktree `publishing/perf-pvp-scalability`.
База: `testnet-pvp-server`, `0e13688f559b0807b334c7e963b938d0107d0959` (fetch проверен).
Финансовый контракт, signer, Mainnet и публичный deployment не менялись. Публичный лимит не повышался.

## Что подтверждено и где проходит граница

Локальный сценарий 50 одновременных матчей / 100 клиентов проходит короткий нагрузочный
прогон после оптимизаций. Полный матч исходного движка воспроизведён в 50 параллельных
мирах с точным совпадением состояний и победителя, без повторных mock-завершений.
Пятиминутный прогон и окончательная проверка запаса приведены ниже.
Это не подтверждение 100 реальных кошельков, пропускной способности NEAR или вместимости Railway.

Машина измерений: Windows, i7-8700K, 12 логических CPU, 32 GiB установленной памяти,
Node 26.13.0. Backend закреплён маской affinity=15 за четырьмя логическими CPU;
это не четыре выделенных vCPU. V8 old space ограничен 6144 MB, жёсткого лимита RSS 8 GB нет.
Docker и рабочий Linux/WSL здесь недоступны. Рецепт настоящего ограничения 4 CPU / 8 GB
подготовлен в `load/Dockerfile` и `load/README.md`, но не запускался. Node 24 production
на этой машине не измерялся. Продакшен-конфигурация 1 vCPU / 1 GB также не измерялась.

## Сценарий и метод измерения

Отдельные controller и backend-процессы, настоящие HTTP, движок и SQLite на диске с
WAL / synchronous=FULL. Каждому прогону принадлежит новая временная БД; пользовательские
сохранения и рабочая БД не очищались. Два клиента на матч, каждый опрашивает полное
состояние раз в 250 мс и раз в 2 секунды отправляет законную команду материала, затем
повторяет тот же ID/sequence. Кеширование, gzip, авторизация и rate limit включены.
Команда может законно вернуть accepted=false, если машина занята или доставка уже сделана;
она всё равно получает последовательный долговечный ответ. Сверяется число обработанных
sequence на сервере и подтверждённых клиентом уникальных команд.

Матчи создаются/присоединяются конкурентно через GameService перед замером;
отдельный admission-прогон проверяет эти гонки через настоящий HTTP. Депозиты в основной
нагрузке моделируются финальными наблюдениями цепочки; это не FT-переводы.
FakeChain по умолчанию задерживает каждый метод на 5 мс. Его счётчики не являются
числом настоящих сетевых JSON-RPC запросов. Он не моделирует очередь signer nonce,
газ, лимит провайдера, callbacks или финализацию блоков.

Каждый клиент имеет отдельный loopback source IP, чтобы не обходить исходный IP limiter.
Во время reconnect-прогона keep-alive соединения всех клиентов закрываются и создаются
заново. Неопределённая команда повторяется с тем же ID/sequence. Ошибки соединения
включаются в результат, а не исключаются из percentile. Перцентили команд включают исходные запросы и идемпотентные повторы.
Перцентили считают ответы включая HTTP-ошибки; transport failures учитываются отдельно. API p95 относится к
этому игровому HTTP-сценарию, не к ожиданию кошелька или on-chain транзакции.

### Корректность и повторные операции

`load/determinism.mjs`: исходные engine/service из 0e13688 провели бот-матч seed=42,
940.3 игровых секунды, 91 законная команда. Этот журнал воспроизведён в 50 мирах
оптимизированного сервера. Полные состояния и сторона победителя совпали, SHA-256:
`56171d893e7ed6758a6e6dea743b15f44d994f6ff443b3e904bf47a153b80759`.
Завершений в FakeChain ровно 50; повторная reconciliation не создала вторых завершений.
Это проверка детерминированности, не timed load и не on-chain выплаты.
`load/routes.mjs`: 1920 точных сравнений маршрутов на 20 seed, обе стороны,
три набора дорог, оба режима диагоналей. Проверено, что изменение возвращённого
маршрута не портит кеш и повторное восстановление дорог даёт прежний результат.

30 backend-тестов и 169 игровых регрессий прошли. Среди проверок: отказ outer COMMIT
с откатом миров/sequence/журнала; прежний signed outbox после неоднозначного RPC;
single-owner lease и backup/restore; reconnect обеих сторон; disconnect и единственный
winner; gzip/304 с проверкой авторизации и обновлением presence; отдельные бюджеты
авторизованных пользователей за NAT. Изолированная Edge QA прошла: обе стороны,
команды, reload, восстановление после начального сетевого отказа, tamper recovery и mobile.
Автономные HTML, включая `build-offline.cjs`, и PvP bundle пересобраны.

## Что изменено

- Геометрические ключи без Array.join; ограниченный кеш маршрутов на мир с полным
  сбросом при изменении дорог. Порядок Dijkstra, стоимость, топливо, рецепты и правила
  победы прежние. Копии маршрутов не разделяют изменяемые массивы с кешем.
- До start/recovery маршруты подготавливаются небольшими порциями с yield event loop;
  холодные расчёты вынесены из первого игрового тика. Цена — больше времени подготовки
  (примерно 4.8 секунды p95 для 50 одновременно подготавливаемых матчей в коротком прогоне).
- Команды из HTTP собираются до 2 мс, максимум 256 в группе, очередь максимум 1024.
  Для переполнения возвращается 503 с указанием повторить прежний ID. Изменения мира,
  снимок и command journal коммитятся вместе при synchronous=FULL. Ответ — после
  COMMIT; внутренние SAVEPOINT изолируют ошибки команд, откат общей транзакции
  восстанавливает все затронутые миры. Прямой command остаётся синхронным.
- Грязные секундные snapshots пишутся одним COMMIT, неизменившиеся пропускаются.
  При reconciliation не пишется заново полный мир, если chain/phase/error/recovery
  не изменились. Prepared statements используются для command journal.
- Монотонное серверное время и фиксированный шаг 100 мс. Необработанный elapsed
  больше не обрезается до 500 мс; максимум пять шагов за pump, остаток остаётся
  backlog и измеряется. Время ожидания лобби не накапливает игровой долг.
- Четыре reconciliation worker вместо последовательного обхода. Heartbeat ставится
  перед обходом; отказ heartbeat не блокирует reconciliation просроченной партии. Signed writes остаются на единственной прежней Chain.tail.
  Только совпадающие in-flight get_match объединяются; финальный block time кешируется
  на одну секунду после получения. Неудачные read promises удаляются из кеша.
- Меню получает metadata без states; game polling использует ETag/304, gzip level 1
  и ограниченный кеш сериализованных ответов. Presence обновляется и при 304.
  На 50 матчах поток полного игрового polling снизился с 1.76 до 0.456 MB/s (около 74%).
  ETag редко помогает во время движения: revision меняется 10 раз/сек; основная экономия
  здесь — gzip и отсутствие ненужных миров у родительского меню.
- Завершённые/остановленные партии освобождают engine caches, журналы остаются
  долговечными. Игра уже ограничивала видимый log 40 строками; это правило не менялось.
- Сохраняется single-owner SQLite lease; основной pump и отправка signed bytes
  проверяют владение. Потеря lease или checkpoint останавливает сервер безопасно.
  Диапазон MAX_ACTIVE_MATCHES расширен до 200 для явной настройки, default всё ещё 10.

## CPU, память и SQLite

CPU-профили: `load/results/cpu-profile-summary.json`. Основные self samples
промежуточного профиля до кеширования маршрутов — key, travelPoint, проверки маршрутов; затем SQLite
и lease-проверки. Профили включают инструментальную нагрузку, поэтому их времена
не заменяют основную таблицу. Полные .cpuprofile сохранены локально в tmp/profiles.

При 50 матчах короткой серии backend использовал 5.73 CPU-секунды за 30.2 секунды
(около 0.19 CPU core в среднем), peak RSS 191 MiB. Это не отсутствие пиков и не
разрешение ужать memory limit до среднего. Секундный checkpoint p95: 38.3 → 7.7 мс.
При 200 матчах checkpoint p95 27.3 мс, суммарное время outer COMMIT около 496 мс за
30 секунд; serialized snapshots/records около 64 MB, конечная БД 3.3 MB.
Показатели serializedBytes — логический объём записей, не физический IO и не IOPS.
Жёсткие характеристики диска, power-loss/fsync и дисковая квота VPS не измерялись.

Наблюдаемые узкие места baseline: холодный routing внутри первого тика, множества
отдельных FULL commits, полные несжатые состояния и последовательная reconciliation.
В этой нагрузке RAM и SQLite не требуют немедленной смены базы. Но все старые match
records со states всё ещё загружаются в память при старте; history list сканирует Map,
command/outbox journals растут. Результат с новой маленькой БД не доказывает ёмкость
с миллионами команд или годовой историей. Аудитные записи не удалялись ради ускорения.

## RPC и условия реальной сети

Отдельно выполнены только публичные Testnet status/block чтения (по 12 на endpoint,
concurrency=1), без env-файла, ключей и транзакций. `rpc.testnet.near.org`: 3.11–3.50 с
на запрос на этом сетевом пути; `test.rpc.fastnear.com`: 115.6–468.5 мс.
Источники — `load/results/rpc-readonly*.json`. Это маленькая выборка и локальный путь,
не SLA провайдера или доказательство QPS. FastNEAR указан в текущей проектной
документации как runtime endpoint, переменные production здесь не читались.

Блокировка API на RPC недопустима для обычных игровых команд; они и snapshot не
вызывают сеть. Но create/join/deposit-template и финальный payout могут ожидать RPC.
Реальная p95 всех финансовых endpoints <500 мс не подтверждена. Один runtime signer
с сериализацией nonce остаётся bottleneck массового create/start/result. Гонка mock
лобби не доказывает реальную скорость подписания/receipt finality.

## Решение о PostgreSQL / Redis и следующий этап

Немедленная миграция для измеренного одиночного процесса с 50 матчами не обоснована.
SQLite оставлен с WAL/FULL и одним владельцем. Redis для корректности игры не нужен.
Следующие изменения — предложения, не реализованные функции:

1. Выполнить Docker-рецепт на выделенных 4 vCPU / 8 GB с настоящим диском: 30–60 минут,
   обе стадии игры, изменяющиеся дороги, больше машин, одновременные reconnect и
   обновление кошельков. Сохранить CPU profile, RSS, backlog, WAL/IO latency и командный
   журнал; повторить минимум три раза. Цель: command/API p95 <500 мс, худший backlog
   и лишняя задержка pump <250 мс, ошибок/потерь/двойных результатов нет.
2. С двумя подготовленными кошельками и mock FT отдельно измерить настоящие
   create → deposit → start → finish → payout. Затем малой согласованной волной
   проверить очередь signer, QPS/429 и receipt finality. Не использовать нагрузочный
   fixture как разрешение на массовые финансовые транзакции.
3. Для RPC: измерять возраст последнего успешного sync/heartbeat по матчу, использовать
   фазовые интервалы и jitter, отдельный ограниченный бюджет финансовых запросов;
   при медленном провайдере возвращать resumable handles вместо долгого HTTP ожидания.
4. До больших историй отделить активные snapshots от архивных, добавить пагинацию
   истории/журналов и проверяемый backup/retention без удаления финансовых ID/outbox.
   Повторить нагрузку с восстановленной большой БД. При устойчивом IO/lock bottleneck
   переносить commands + match snapshot + outbox атомарно в PostgreSQL.
5. Для нескольких authority workers сначала ввести durable match ownership с fencing
   epoch, проверкой owner/version при каждой записи и уникальными operation IDs.
   Signer dispatch/nonce должен иметь одного durable владельца. Только затем разделять
   матчи по процессам; несколько серверов над общей SQLite здесь запрещены.
   Redis можно добавить для эфемерных presence/cache/rate budgets, не для хранения
   единственного источника команд, результата или подписанной транзакции.

Порог для следующего performance-разбора: устойчивый checkpoint/commit p95 >50 мс,
backlog >250 мс, command/API p95 >500 мс, растущая очередь RPC или невозможность
своевременного heartbeat. Это предложенные эксплуатационные сигналы, не текущий SLA.
Рекомендуемый публичный лимит не повышать автоматически до проверки выделенного хоста
и отдельной настоящей финансовой приёмки. Mainnet остаётся вне задачи.
