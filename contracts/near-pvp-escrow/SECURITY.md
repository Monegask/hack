# Модель безопасности и ограничения

Контракт предназначен для Testnet-проверки. Этот документ описывает реализованные ограничения, а не гарантирует безопасность реальных средств.

## Доверенные стороны

**Игровой сервер** авторитетно определяет результат, закрепляет участников, передаёт принятые условия и сообщает off-chain активность. Сервер способен выбрать любого участника победителем или поддерживать heartbeat зависшей игры. On-chain heartbeat доказывает факт серверной транзакции, а не исправность игрового процесса. Для защиты от злонамеренного, но отвечающего сервера нужны независимые attestations, dispute protocol или иной дизайн; это не входит в ТЗ.

**USDC token** определяет балансы и корректность NEP-141, может обладать freeze/blacklist/pause/upgrade. Если токен возвращает успешный ft_transfer без перевода, escrow не может это обнаружить. Поэтому token ID неизменен и его проверка обязательна. Получатель может удалить регистрацию: выплаты останутся его обязательством и потребуют регистрации + claim. Прямой ft_transfer без msg не создаёт ставок и может оставить невостребованный излишек.

**Администратор** может остановить новые активации и отменить незавершённый матч полным возвратом. Это влияние на доступность/честность игры. Администратор не получает метод вывода ставок или назначения победителя, не меняет stake/fee существующего лобби. Замена server разрешена только в paused+drained состоянии. Admin может смениться двухэтапно; исторический fee_receiver сохраняется.

**Deployment/Full Access Key** escrow-аккаунта способен выполнить DeployContract вне публичного Rust API и заменить все ограничения. Политика upgrade в коде не устраняет эту возможность. Не заявляйте, что администратор физически не способен злоупотребить депозитами, если он контролирует этот ключ. Управляйте им через независимый multisig/governance с собственным запретом обхода; сохраняйте владельца/политику в эксплуатационной документации. Удаление всех full access keys ограничивает пути управления, но требует отдельного проверенного governance-контракта для последующих обновлений.

## Реализованные меры

| Угроза | Защита |
|---|---|
| Неправильный FT, sender, сумма, match, revision | Полное отклонение через NEP-141 resolver, без финансовой мутации |
| Подмена участников / два активных матча | Закреплённый состав + active index; self-opponent запрещён |
| Изменение условий после оплаты | Первый accepted deposit блокирует update_stake, msg фиксирует revision/stake/fee |
| Фальшивый result / callback | predecessor server; winner участник; callback private+self+один promise result |
| Двойной payout / конкурентный claim | Запись InFlight до promise, attempt nonce, Paid идемпотентен |
| Result против refund / cancel против start | Атомарные receipt-переходы и проверки state/time |
| Неправильное округление / overflow | u128, checked arithmetic, fee quotient/remainder, нулевые переводы пропускаются |
| Потерянный backend / зависший матч | Необратимое истечение индивидуального heartbeat, самостоятельный полный refund |
| Replay mutual cancel | ID + возрастающий nonce, подтверждает другой кошелёк |
| Разрастание storage | Серверное создание, cap записей, запас native NEAR, prune после оплаты |
| Подмена payout recipient | Получатель записывается при решении; claim не принимает новый адрес |

Самостоятельный forfeit относится к авторизации участника, а не полномочию admin назначать победителя. Admin, выступающий игроком собственного матча, имеет только те же participant-права.

## Асинхронные ограничения

Ошибка FT восстанавливает только исходное Ready-обязательство. Callback success, включая ответ сверх лимита чтения, считается успехом ровно один раз. FT transfer использует 25 Tgas, callback 20 Tgas; end-to-end проверено с проектным standards FT. Для Circle требуется отдельный live transfer test, т.к. стоимость и политика FT могут отличаться.

Если сам callback не выполнится (например, protocol/runtime failure), состояние может остаться InFlight. Его нельзя безопасно вернуть в Ready по таймауту: деньги уже могли быть отправлены. Нужны расследование final receipts, устранение инфраструктурной ошибки и отдельно проверенная процедура восстановления; публичного admin override выплаты нет. Это ограничение доступности при выборе защиты от двойного вывода. Upgrade gate остаётся закрытым при таком обязательстве.

Native NEAR-пополнение может потребоваться любому лицу через fund. Недостаток gas/NEAR при dispatch сохраняет Ready. Нельзя оплачивать операционные расходы из ставок. Жизненный цикл не имеет произвольного token sweep.

## Эксплуатационные проверки

Мониторьте accepted=locked+owed+paid; in_flight и длительность callbacks; coverage heartbeat каждого матча; native NEAR и storage; FT pauses/blacklisting; failed receipts и Ready payouts. Остаток FT сверяется с обязательствами после завершения всех in-flight операций, с отдельным учётом unsolicited transfers.

Перед реальными ставками необходимы независимый аудит кода/миграций, проверка ключевой политики и отдельная юридическая проверка допустимости механики в целевых юрисдикциях. Автоматический Mainnet deployment отсутствует. Приватные ключи не входят в репозиторий; Testnet CLI сохраняет их только в явно указанном абсолютном каталоге за пределами репозитория с правами 0700/0600 на Unix.
